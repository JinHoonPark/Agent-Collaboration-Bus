# M1 착수 전 미검증 항목

스펙(`../Specs/ACB-spec-v0.2.md`)에서 옮겨온 목록이다. 스펙은 무엇을 만들지를 정의하고,
이 문서는 만들기 전에 확인해야 할 것을 다룬다.

## 착수 순서 — 왕복 1회를 가장 먼저 통과시킨다

지금까지 확인된 것은 전부 "외부 스크립트 → 훅 → 에이전트 세션 1개" 구조다.
**에이전트 두 개가 요청·응답을 완주한 적이 없다.**

남은 위험은 배관 코드가 아니라 **모델 행동**이다. 수신 에이전트가 메시지를 처리하고도
`acb_reply` 를 호출하지 않고 자기 사용자에게 보고만 하고 끝낼 수 있다. 이는 확률적이라
코드로 보장되지 않으며 실제로 돌려봐야만 안다.

따라서 M1 은 "브로커를 다 만들고 마지막에 테스트"가 아니라, **`acb_register` /
`acb_send` / `acb_inbox` / `acb_reply` 최소 경로로 A → B → A 왕복 1회를 먼저 통과시키고**
그 위에 나머지(대시보드, 에러 처리, 정리 잡)를 얹는 순서로 진행한다.
800 LOC 를 다 쓴 뒤에 행동 문제가 드러나면 되돌리는 비용이 크다.

## 확인 항목

| 항목 | 왜 미검증인가 | 확인 시점 |
|---|---|---|
| **`Mcp-Session-Id` 안정성** | 스펙 6.1 의 세션 바인딩 설계 전체가 이 전제 위에 있다. 유지되지 않으면 모든 툴이 `session_token` 을 인자로 받는 방식으로 폴백하고 6장 시그니처를 전부 고쳐야 한다 | **M1 최우선. 코드 작성 전** |
| **에이전트 간 왕복 전체** | "외부 스크립트 → 훅 → 에이전트 1개" 구조로만 확인했다. 두 에이전트가 요청·응답을 완주한 적이 없다 | **M1 최우선** |
| 수신 에이전트가 실제로 `acb_reply` 를 호출하는가 | 메시지를 처리하고도 자기 사용자에게 보고만 하고 끝낼 수 있다. 확률적 행동이라 코드로 보장되지 않는다 | M1 왕복 테스트 |
| 훅 주입 지시를 **MCP 툴 호출**로 일반화 | 지금까지는 파일 읽기/쓰기 지시로 확인했다. 실제 ACB 는 `acb_inbox` 호출을 지시한다 | M1 통합 테스트 |
| **Streamable HTTP** 전송에서의 elicitation | stdio 로만 확인했다. ACB 는 스펙 9장대로 Streamable HTTP 를 쓴다. 안 되면 OS 알림으로 폴백 | M1 브로커 기동 시 |
| HTTP 전송에서 "세션 1개 = 연결 1개" | stdio 에서는 클라이언트마다 서버 프로세스가 따로 뜬다. HTTP 는 구조가 다르다 | M1 |
| `acb_wait` 반복 폴링을 모델이 견디는가 | 45초 블로킹 툴을 반복 호출하는 동안 포기하거나 다른 작업으로 새지 않는지 확인하지 않았다 | M2 |
| 다건 동시 배달, `additionalContext` 2,500 토큰 초과 시 축약 동작 | 단건으로만 확인했다 | M2 |
| 툴 호출 **진행 중**의 elicitation | 전부 idle 상태로만 확인했다. Codex 바이너리에 `guardian MCP elicitation metadata must include a non-empty tool_name` 문자열이 있어 Guardian 경로에서는 툴 연결을 요구하는 것으로 보이나 동작은 확인하지 않았다 | M3 notify 구현 시 |
| 자동 거부 판별 임계값 | 자동 거부는 수 ms, 사람 응답은 최소 수십 초. 그 사이 어디에 선을 그을지 정하지 않았다 | M3 |
| Codex CLI 의 마켓플레이스 배포 경로 | `hooks.json` 과 `config.toml` 의 `mcp_servers` 를 쓴다는 것까지만 확인됐다 | M6 |
